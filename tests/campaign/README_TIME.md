# Campaign time checks (package 2)

```powershell
$godot = 'C:/Users/Symok/Downloads/Godot/Godot_v4.7.2-stable_win64.exe/Godot_v4.7.2-stable_win64_console.exe'
& $godot --headless --path . --script tests/campaign/run_time.gd
& $godot --headless --path . --script tests/campaign/run_time.gd -- --quick
python tests/campaign/run_time_oracle.py --godot $godot --workers 12
python tests/campaign/tools/make_time_fixtures.py --check
```

`run_time.gd` prints `CAMPAIGN_TIME_PASS` and is registered in `tests/run_headless_checks.py` with a 30-minute limit, because it includes one full 86,400-tick detailed oracle day (about three minutes here). `--quick` skips only that day and prints `CAMPAIGN_TIME_QUICK_OK` instead, so a quick run can never satisfy the runner.

Every equivalence scenario runs the same v3 commands on two real facades, one in `detailed` (oracle) mode and one in `auto` (replay) mode, then compares the complete checkpoint, the emitted event list and the next RNG draws. The declared tolerance is abs 0 / rel 0; each `TIME_EQUIV` line prints the deviation actually found. Scenarios: battery saturation, reserve exhaustion (danger stop), power shortage, input-limited production, wastewater overflow, crew travel and labor, an expedition, scheduled RNG boundaries, an unmodeled hook (forced fallback), a registered hook flow, ordinary 20x play and frame splitting. Other sections cover the calendar, pacing, strict commands, paused queues, cancellation, save mid fast-forward, schema rejection, schema-1 migration and bounded frame work.

`long_horizons` runs a week and 200 days on the replay path. It checks the stops at the day-150 order deadline and the day-180 shipment, and opens oracle windows (both modes continued from the same checkpoint) after each day of the week, across battery saturation and after the shipment boundary. That is partial oracle coverage for those horizons.

`run_time_oracle.py` is the full comparison for the week and the first 180 days. The replay run writes a checkpoint per segment; a separate one-second oracle process replays each segment from the previous checkpoint and must reproduce the next one byte for byte. Exact comparisons chain, so the segments run in parallel. It takes tens of minutes and is not part of the normal runner. Its output is `TIME_ORACLE_PASS`.

## Fixtures

`tests/campaign/fixtures/` is generated by `tools/make_time_fixtures.py` from the Task 01 habitat fixture; do not hand-edit it. All values are synthetic. `time_sustainable` declares stocks and capacities large enough for 180 days **without food production**. That is a test boundary: it does not show a self-sufficient habitat, and nothing here claims the real campaign survives 180 days before agriculture exists. `time_battery_near_full` and `time_food_exhaustion` place a saturation and an exhaustion a few minutes in. The legacy presets `power_shortage_6crew`, `habitat_5crew`, `storage_limits_6crew` and `salvage_6crew` are used unchanged.
